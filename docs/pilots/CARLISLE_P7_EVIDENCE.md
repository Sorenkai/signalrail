# Carlisle P7 evidence matrix: infrastructure evidence and route recovery

P7 (DECISION_LOG D-037). Investigated on 2026-10-28 on branch `phase1-carlisle` (HEAD `6acbb0d`, P0–P6 uncommitted and preserved). The service counts come from the planner (`buildServicePlan`) on the unchanged DFROC1F snapshot `carlisle/timetables/2026-11-04.json`, through `docs/pilots/carlisle-p7-coverage.json`. A count of "services potentially affected" is an upper bound. Each of those services would still need every other blocker of its group removed and an exact pattern. Only the planner's classification is a result.

Physical facts (track, connections, crossings) and signalling facts (signal function, points lie, routes, locking, overlaps, flank, authority to pass a signal) are kept apart throughout. A map showing a track connection does not show any signalling fact.

**Validation (implemented):** the existing checks already stop a two-edge switch from being treated as a modelled junction:

- the dataset validator warns (`SWITCH_TOPOLOGY`);
- game rules reject it (G3, `GAME_RULE_POINTS_INVALID`; now tested for `osm-pts1460504022`);
- routes over it are `ROUTE_SWITCH_UNRESOLVED`, so `insufficient_evidence`;
- `TrackGraph` never passes it.

One runtime path remained: `move_points` accepted points on any node and reported them "detected". P7 refuses it with `POINTS_TOPOLOGY_INCOMPLETE` for every junction class `incomplete`. At Carlisle that is the five in-play two-edge switches (D-037).

| A diamond whose tracks cross without connecting | Yes, physically: a `crossing` node with four edges. The graph never passes it (`switchPassage` is `unresolved`), so it introduces no connection. It cannot carry a route | **Proposed, not implemented** (no service would gain). `switchPassage` would pass a crossing straight across only between the two edges of one source way running through the node (sourced continuity).
